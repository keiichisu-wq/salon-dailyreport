ARTEX脅威動向レポート

AIエージェントによって、サイバー攻撃の速度・規模・継続性がどう変わるか

2026年11月15日版｜経営層・事業責任者向け
ARTEXの本質は「新しい攻撃手法」ではなく、既存の攻撃を自動で探し、組み合わせ、失敗しても再試行する攻撃オーケストレーターである。
01 / OVERVIEW

ARTEXとは

ARTEXは、LLMと複数のAIエージェントを使って、侵入テストの工程を自動化するオープンソースのフレームワークです。本来は正規のセキュリティ検証を目的としていましたが、犯罪者や国家系と評価される攻撃者による悪用が確認されています。

攻撃者が「この企業の機密情報を探す」「管理者権限を取得する」といった目標を与えると、ARTEXは計画を作り、既存の攻撃ツールやクラウドAPIを呼び出し、結果を共有しながら次の行動を選びます。

AIモデルではない 複数の商用・オープンソースモデルを切り替えて利用できる基盤
単体マルウェアではない 既存ツール、API、外部サービスを連携させる指揮・自動化レイヤー
攻撃者専用ではない 正規のペンテストにも使えるが、同じ能力が実攻撃に転用されている
02 / ATTACK FLOW

ARTEXはどう動くか

1. 攻撃者が目標を指定

標的、目的、窃取済み認証情報などを与える。

2. 自動偵察

公開アプリ、API、GitHub、クラウド、AD、認証画面を探索する。

3. 複数経路を並列実行

パスワードスプレー、認証・認可不備、漏えい鍵、公開管理APIなどを試す。

4. 結果を評価して再試行

失敗理由を分析し、パラメータ、ツール、侵入経路を変更する。

5. 権限昇格・横展開・永続化

OAuth資格情報、管理者アカウント、Webシェル、RATなどを利用する。

6. データへ到達

メール、DB、Key Vault、クラウドストレージなどを収集・持ち出す。

03 / MACHINE SPEED

最大の変化は「時間」

攻撃者が手作業で行っていた調査、判断、修正が自動化され、防御側が対応を判断している間に次の工程へ進みます。

2〜25秒 観測された実行バースト
5分以内 公開鍵の発見からKey Vault取得
8万件／90分 関連事例のリクエスト量
経営上の問題：「検知できるか」だけでなく、検知後に何分で認証情報を失効し、アプリを止め、システムを隔離できるかが問われる。
04 / BUSINESS IMPACT

企業に与える5つの影響

対応時間の消失

検知から会議、承認、封じ込めという人間中心の手順では間に合わない可能性がある。

攻撃対象の拡大

一組織あたりの攻撃コストが下がり、知名度に関係なく弱点のある企業が狙われる。

周辺システムの入口化

取引先ポータル、モバイルAPI、古い業務システム、事業部独自アプリが攻撃経路になる。

サプライチェーン波及

一つの委託先や連携アプリの侵害が、多数の顧客テナントへの攻撃機会に変わる。

正規操作への偽装

正しい認証情報や管理APIを使うため、IPやマルウェアだけの監視では見つけにくい。

攻撃スキルの平準化

計画、ツール選択、エラー修正をAIが補助し、少人数でも複雑な攻撃を実行できる。

05 / OBSERVED CASES

確認されている活動

  • VAPOR PANDA：14か国以上、200組織以上を対象とし、9組織で侵入後の活動が報告された。
  • STORM-0940：侵害された第三者アプリの認証情報を利用し、2,250以上のMicrosoft 365下流テナントへのサインインを試行した。
  • STORM-3358：東南アジアの金融分野などを対象に、公開システムを侵害してRATやC2ツールを展開した。
  • 韓国金融機関：ARTEX関連の攻撃で、約6万7,000人分の個人情報流出が報告された。
  • クラウド秘密情報：公開GitHubから認証情報を発見し、5分以内にAzure Key Vaultからデータを取得した事例が報告された。

数字は異なる調査・キャンペーンの集約であり、一つの攻撃ですべてが発生したものではない。2,250テナントすべての侵害が確認されたわけでもない。

06 / EXPERT ASSESSMENT

大元氏の評価をどう反映するか

確認できた関連公開投稿では、「高度な認証だけでは十分でない」「従来型の脆弱性診断だけでは、設定・管理・信頼関係の弱点を捉えきれない」「脅威モデリングが重要」という問題提起が示されています。

妥当

ARTEXは強固な正面を避け、弱い経路を探す

FBI、Google/Mandiant、Talosも、周辺アプリ、公開API、漏えい鍵、取引先との信頼関係が悪用される点を報告しており、この評価と整合します。

表現に補足が必要

「MFAは効かない」ではなく「MFAだけでは足りない」

MFAはパスワードスプレーや盗難パスワードの悪用に有効です。一方、アプリ資格情報、API認可不備、既存セッション、信頼済み第三者アプリなど、MFAを通らない経路は防げません。

表現に補足が必要

「脆弱性診断が無効」ではなく「従来型診断だけでは不十分」

既知脆弱性の診断は引き続き必要です。ただし、認証・認可、設定、クラウドIAM、業務API、組織間の信頼経路まで含めた脅威モデリングと侵入シナリオ検証が必要です。

レポートへの反映方針：個別製品を否定するのではなく、「単一対策では止められず、攻撃面全体と侵入後の影響を管理する必要がある」と表現する。
07 / PRIORITIES

優先して実施すべき対策

公開資産と周辺システムを把握する

取引先ポータル、古いAPI、管理画面、モバイルバックエンドを含めて棚卸しする。

秘密情報とサービスIDを管理する

公開コード、CI/CD、設定ファイルをスキャンし、長期鍵を短期・用途限定の認証へ移行する。

信頼関係と権限を最小化する

OAuthアプリ、サービスプリンシパル、委託先アクセス、クラウドロールを定期的に見直す。

速度と量を検知する

短時間の大量API、連続する権限エラー、通常と異なるアクセス元を横断的に相関分析する。

封じ込めを機械速度に近づける

トークン失効、アプリ無効化、システム隔離を事前承認し、演習で実行時間を測定する。

08 / CONCLUSION

経営層への結論

ARTEXの脅威は、AIが未知の攻撃を発明することではない。既存の弱点を機械速度で発見し、複数経路を試し、最も弱い場所から侵入して被害を連鎖させることである。

したがって対策の中心は、「ARTEXというツールを検知すること」ではありません。認証情報が一つ漏れても被害が広がらない設計と、異常を検知した瞬間に認証・アプリ・システムを止められる体制です。
